# 异议应对库 · Objection Handling

> 来源：真实客户异议，按类型归档。
> 每个异议 = 「逻辑 + 话术 + 适用边界」。

## 异议类型

### 1. 太贵了 / 预算不够
**逻辑**：不是降价，而是「把价值拆开算账」或「降低首次决策门槛」。
**话术**：
- 「我理解。换个角度算：这套系统省下的人工/时间，折算成钱大概 [X 元/月]，投入是 [Y]，相当于 [X/Y] 个月回本。我们算给你看。」
- 「如果不想一次到位，可以先从 [最小模块] 试，几千块验证效果，再决定要不要扩。」
**边界**：若客户确实预算不足 → 不硬推，转入「引流品」长期培育。

### 2. 我们不需要 / 现在没这个打算
**逻辑**：用场景反问，定位真实需求；不强推。
**话术**：
- 「完全理解。方便问一下，你们现在 [某流程] 这块是怎么处理的？」
- 「其实很多客户一开始也这么觉得，后来发现 [具体场景] 里还是有明显痛点。你这边有类似情况吗？」
**边界**：确认无需求 → 礼貌收尾，保持联系入口（内容持续触达）。

### 3. 再看看 / 我考虑下
**逻辑**：给「对比工具」，约定明确跟进时间。
**话术**：
- 「没问题。给你一份 [对比清单/验收标准]，方便你评估时参考。我 [具体日期] 再跟你同步一个信息，可以吗？」
- 「很多客户最后选不选我们都没关系，关键是别因为信息不全做了错误决策。」
**边界**：约定时间必须跟进，否则失联。

### 4. 怕没效果 / 担心白花钱
**逻辑**：案例 + 阶段性验收 + 风险承诺。
**话术**：
- 「你的顾虑很合理。所以我们把交付拆成 [3 个验收节点]，每个节点你确认效果再继续。」
- 「这是 [同类客户] 的真实数据，[指标] 从 [X] 到 [Y]。你们的规模和场景类似，可参考。」
- 「如果 [某个关键指标] 没达标，[退款/免费延期/只付成本] —— 我们敢承诺是因为流程跑透了。」
**边界**：承诺必须真实可执行，不可过度承诺。

### 5. 我们自己能做 / 有技术团队
**逻辑**：强调「业务落地能力」而非「技术能力」。
**话术**：
- 「技术团队自己搭没问题，我们更多是帮你少踩坑 —— [同类客户] 自己做了 6 个月没跑通，我们 6 周上线。」
- 「可以把它当成『咨询 + 框架 + 验收标准』，你们团队来执行也可以。」

### 6. 数据安全 / 私有化顾虑
**逻辑**：明确技术方案 + 合规承诺。
**话术**：
- 「数据完全不出 [你的环境]，我们支持私有化部署，代码/数据都在你这边。」
- 「这部分我们签 [保密/数据处理协议]，法律上约束清楚。」

## 提炼规则
- 每条异议必须来自**真实记录**（lead-log.csv 的备注）。
- 话术要可复现，不是临场发挥。
- 每季度回看：哪些异议被「案例 + 验收承诺」化解了 → 沉淀为销售资产。

## 数据化追踪
- 记录到 `lead-log.csv`：每条线索的异议类型、应对方式、最终结果。
- 月度统计：哪种异议最常见、哪种应对最有效 → 反哺本库。
