# /gzo — 公众号增长操作系统总入口

> 设计参考：[dbskill](https://github.com/dontbesilent2025/dbskill) 的 `/dbs`。
> 你**不需要**先学会哪套方法，也不需要知道该调用哪个 Skill。把当下的业务、材料、选择或卡点交给 `/gzo`，它会根据上下文判断单项还是组合。

## 编排规则（固定，不可破坏）

```
真实任务
  ↓
/gzo 读取上下文 → 判断：单项 or 主+辅组合
  ↓
生成一段可直接继续发送的提示词（说明推荐理由）
  ↓
入选 Skill 交付一份统一结果
  ↓
补充结果与反馈 → 再次 /gzo → 重新编排
```

- **单个 Skill 能覆盖 → 保持简单。**
- **任务包含独立且必要的要求 → 1 主 + 最多 2 辅，共同交付一份结果。**
- 每轮**只处理一个当前任务**，不在一次调用里堆所有事。

## 调用方式

**让 Agent 自动判断（推荐）：**

```
/gzo 我们公众号写了两个月，阅读一直在 200 左右，但几乎没有咨询。
```

Agent 会说明推荐理由，例如：「诊断发现堵点在销售承接（线索→沟通转化低），主 Skill `gzo-diagnosis`，辅以 `gzo-convert` + `gzo-content`」，然后生成一段可直接发送的提示词。

**已经知道需求时，直接调用具体 Skill：**

```
/gzo-topic      我想讲「中小企业为什么不该一上来就上大模型」，这个选题怎么做成爆款？
/gzo-content    按这篇文章骨架把初稿写出来
/gzo-convert    设计一个把读者引流到企业微信的钩子
/gzo-data       看这周的数据，判断下周该押注哪个选题方向
/gzo-product    把最近 20 个客户的异议整理成产品迭代清单
```

## 完整 Skill 目录

| Skill | 职责 | 何时用 |
|---|---|---|
| `gzo-diagnosis` | 业务诊断：定位流量/销售/产品哪个环节卡住 | 数据下滑、增长停滞、不知道问题在哪 |
| `gzo-topic` | 选题：从知识库+热点生成可验证的选题假设 | 今天写什么、选题会 |
| `gzo-content` | 写作：标题/钩子/正文/CTA | 有选题，要成文 |
| `gzo-publish` | 发布：排版、定时、多平台分发 | 成文后发布前 |
| `gzo-traffic` | 流量：投放/分发/SEO/私域引流 | 阅读量上不去、要扩渠道 |
| `gzo-convert` | 销售转化：钩子、私域承接、成交话术 | 有流量没线索、有线索没成交 |
| `gzo-product` | 产品：从反馈提炼需求、定价、交付 | 客户异议集中、产品要迭代 |
| `gzo-data` | 数据复盘：日/周/月报表 + 归因 | 每天/每周/每月固定动作 |
| `gzo-archive` | 归档：沉淀知识原子、更新知识库 | 一轮结束后沉淀 |

## 输入约定（给 Agent 的规范）

调用任何 Skill 时，Prompt 中应包含：
1. **当前任务**（一句话）
2. **已知事实**（最新数据、客户反馈、已发布的文章）
3. **约束**（题材范围、合规红线、品牌调性）
4. **期望产出**（要什么格式、给谁用）

## 更新机制

类比 dbskill 的「更新不破坏本地存档」：
- 知识库、SOP 更新 → 只**追加**到 `knowledge/` 与 `skills/`，不覆盖旧内容。
- `archive/` 永不删除。
- `data/` 每日追加 CSV，历史可回溯。

## 触发示例（few-shot，供 Agent 参考编排决策）

**示例 1（单项）：**
> 用户：「帮我给这篇稿子起 10 个标题」
> → 仅 `gzo-content`（标题属于写作子任务）

**示例 2（主 + 1 辅）：**
> 用户：「我想讲『别急着上大模型』，做成爆款还要能引流到私域」
> → 主 `gzo-topic`（选题假设） + 辅 `gzo-convert`（CTA/引流钩子）

**示例 3（主 + 2 辅，满编）：**
> 用户：「我们阅读量有，但几乎没咨询，整体诊断一下，顺便改内容方向和成交话术」
> → 主 `gzo-diagnosis`（定位卡点） + 辅 `gzo-content`（内容方向） + 辅 `gzo-convert`（成交话术）
